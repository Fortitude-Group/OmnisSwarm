# Spike: how Claude Code mods behave (recorder and pane)

Date: 2026-10-21. Claude Code 2.1.306 on Windows 10, Node v24.19.0.

## Summary

Most of what the recorder needs is there, and the payloads are richer than the spec assumed. The agent id in
`agent.spawn`'s result is exactly the id in the subagent's transcript file name. Every subagent tool call carries
`agentId`, the lead's never do, and `turn.complete` fires once per subagent run with that id. The big change is Q5: a
hooks module runs with no Node at all. It can import only its own files (by relative path) and `claude-code`, so
`src/core/log.ts` with `node:fs` can't load in a mod. `$.fs` has read and whole-file write but no append, no offset
reads, a 4 MiB cap per file and writes that aren't atomic. That rules out the mod appending to the log or following
transcripts by byte offset. Two things replace them. `turn.step` hands over each model request's token usage with its
`agentId`, so the transcript reader isn't needed for tokens. And the mod can call its own plugin's MCP server through
`$.mcp.call`. That server is a normal Node process, already runs our `.ts` with no build, and starts in the project
directory, so it becomes the single writer of the event log. The pure parts of `core` (events, fold, stats, prices)
can still be imported by the mod as long as they import nothing from Node.

## How this was checked

- Docs: the `plugin-authoring` skill's `reference.md` and the engine's own `types/claude-code.d.ts` for this build
  (cited below as `d.ts:<line>`, the copy the skill wrote for 2.1.304), plus the official
  [mods reference](https://code.claude.com/docs/en/plugins/mods/reference) and
  [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference).
- Cross-check: RuFlo's working mods, `ruflo-swarm/0.3.7/hooks/register.ts` and `ruflo-console/0.44.6/hooks/`.
- Probe: a throwaway plugin in the session scratchpad (`omnis-probe`), with hooks on `session.start`,
  `classic.SessionStart`, `turn.start`, `turn.step`, `turn.complete`, `session.measure`, `session.end`,
  `session.send`, `agent.spawn` and `tool.call`, logging key shapes only (strings cut to 120 chars). It also declared an
  MCP server that records its own start-up and exits. Run headless from an empty scratch folder:
  `claude --plugin-dir <scratch>/omnis-probe -p "Spawn one general-purpose agent named probe-worker. ..."`.
  Headless loaded the mod: 49 events logged. Session `dd60181f-79e4-43c2-9346-5b2af987d4c1`.
- Q5 and Q6 were also checked with `claude plugin validate` and `claude plugin test` on two more scratch plugins.

Every log line quoted below is from that run unless it says otherwise.

### Also found

- **`turn.step` gives per-request usage with `agentId`.** A generator hook (`yield* next(e)`) gets the step's result:
  `usage: { input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens, model }`, `stopReason`
  and the tool names. That is exactly what `agent.usage` needs, live, with no file following. It lacks the 5-minute /
  1-hour split of cache writes, which the transcript has under `message.usage.cache_creation`. The transcript also writes
  several lines per response (8 assistant lines for the subagent's 5 requests here), so a file reader would have to
  dedupe by message id anyway. Log: `turn.step {"in":{...,"index":0,...,"agentId":"a8c5eb3dd61a2b303"},"usage":{"input_tokens":2,"output_tokens":210,"cache_read_input_tokens":0,"cache_creation_input_tokens":42374,"model":"claude-opus-5-5"},"stopReason":"tool_use","toolUses":["ToolSearch","Glob"]}`. `d.ts:14328-14430`.
- **Function hooks needed no environment variable.** A second headless run with `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS`
  removed from the environment (and not in `~/.claude/settings.json`) still loaded the mod and logged 14 events. What
  can turn mods off on 2.1.306 is policy: `disableAllHooks`, `allowManagedHooksOnly`, `allowManagedModsOnly`
  (mods reference, Settings).
- **Event order for a spawn**, as logged: lead `tool.call:in` (Agent) → `agent.spawn:in` → subagent `turn.start` →
  `agent.spawn:out` → lead `tool.call:out`. The probe's own Agent `tool.call` hook was still waiting while the
  subagent's first events reached it, so holding `next` on the Agent call doesn't hide the child's events.
- The subagent hands its final report back through a `SubagentHandback` tool call (`tool.call` with `agentId`), and
  loads deferred tools via `ToolSearch` calls. Both will show up as `agent.tool` events of kind `other`.
- `agent.spawn` also fires for teammates (`isTeammate`) and workflow agents (`workflow`), and its input has `name`,
  `subagentType`, `description`, `background`, `parentAgentId` (absent from main) and `parentModel`. `parent` in
  `agent.started` comes straight from `parentAgentId ?? 'lead'`.
- `$.agent.list()` right after the spawn returned `[{ id, description, type, status: "running", name }]`, a cheap way to
  reconcile state after a hot reload.
- A hook has a 10 s budget of its own time (time inside `next` or a `$` call doesn't count). Observe-only hooks should
  `return next(e)` and do their work around it.

## Changes for phase 2 and 3

1. **Recorder writes through the MCP server.** The mod builds each event and calls an internal MCP tool (say
   `omnis_record`) with `$.mcp.call`. The server validates and appends with `core/log.ts`. One writer, no torn lines
   from two processes. Recorder handlers never await the call before `next` (fire and forget, errors swallowed), so
   a slow server can't slow the session. The tool should be refused for the model at `tool.check`, so only the mod
   uses it.
2. **Keep `core` split Node-free.** `events.ts`, `fold.ts`, `stats.ts` and `prices.ts` must not import `node:*`, so
   the mod (and later the WebGL window) can import them by relative path. `log.ts` stays Node-only.
3. **Replace the transcript reader with `turn.step`.** Record `agent.usage` from each step's `usage`
   (`cacheWrite5m = cache_creation_input_tokens`, `cacheWrite1h = 0`, so cost from cache writes is a slight
   underestimate when 1-hour caching is on, and stays labelled ≈). If the 5m/1h split turns out to matter, move
   transcript reading into the MCP server, which has Node and byte offsets. The mod can't do it: no offset reads and a
   4 MiB cap, and a trivial subagent's transcript was already 450 KB.
4. **Messages from `session.send`**, after `next`, only when `isDelivered`. `to` is logged as given, and `fold` maps
   `main` to `lead`.
5. **`agent.finished` from `turn.complete` with `agentId`**, reasons mapped as in Q3. Agents can run again after
   finishing (resume, teammates).
6. **New `session.measure` event** for context % and Claude Code's own session cost.
7. **The pane reads state from the MCP server too.** `$.fs.read` caps at 4 MiB and can't read from an offset, so
   following the log file from the mod won't scale. Either an internal MCP tool returns the folded state (or events
   since a sequence number), or the pane folds the events the recorder itself just sent, seeded from the server once at
   open. Phase 3 picks one. Animation uses `$.clock.every` + `$.ui.blit`, under 1024 colour pairs per frame and within
   512x256 cells.
8. **Pass the project root to the server** as `"env": { "OMNIS_PROJECT_DIR": "${CLAUDE_PROJECT_DIR}" }`.

## Not verified

- Blit throughput and how the 1024-pair palette looks in practice: needs an interactive terminal session.
- Whether `session.measure`'s `cost.usd` includes subagent spend. The docs say "summed over every priced API
  response this session". I didn't reconcile the numbers.
- Behaviour under an interactive session generally. Everything above came from `-p`, `claude plugin validate` and
  `claude plugin test`. Nothing in the docs suggests the events differ interactively, apart from `surface` and
  `isInteractive` in `session.start`.
